# 工作指南
欢迎加入 ALTSYNC 开发团队，这是一支充满创意和激情的团队，致力于探索最新的技术与打造捉鱼的产品。无论你是刚入职的彩笔，还是已经熟悉工作的团队成员，该指南旨在帮助你了解团队的开发流程、写作方式以及团队分工职责。

ALTSYNC 的目标是：快速交付产品，实现商业价值，探索前沿技术，同时让所有成员皆有所得。请仔细阅读本指南，本指南将会成为你日常工作中的宝贵参考。

## 核心理念
* 快速开发：聚焦于完成最小可行产品，尽早将产品推向市场。
* 灵活高效：使用部分 Scrum 与看板方案，确保需求能被妥当记录而不遗漏。
* 学习与成长：批判性思考，鼓励探索、使用甚至创造新技术，分享知识。
* 协作共赢：开放性沟通，互相支持，让团队成为高效协作的整体。
* 重视精神与心理：关注每位成员的精神卫生，在尽量不干涉的原则下平衡所有人的精神状态。

## TL;DR
* 工作流程：任务用看板管理，迭代周期为一周，包含计划会、每日站会、成果展示。
* 规则：汇报问题需在群内公开，任务记录清晰，实习生严禁私聊求助。
* 沟通优先：遇到问题及时沟通，团队会支持你成长。
* 透明化沟通：主动指出问题是对团队负责的表现，避免隐瞒或单独解决。

## 工作流程
ALTSYNC 采用了`部分Scrum与看板`的工作流程。

纯 Scrum 对需求快速变化的场景来说不够灵活，而且对于新手来说过于严格的规则容易上手困难。因此，ALTSYNC 仅采用了 Scrum 中适合我们的部分，加上看板为核心的记录方式。

### 任务管理
为了让任务更加清晰可见，我们采用了看板 (Kanban) 来管理任务。为了实现最简化任务编辑，我们使用了共享 Word 文档。在文档中，除去标题和文内注释，每行一条任务。

看板的任务状态流转如下:
1. 待开始 - 在 Word 文档中，没有被认领的任务均为待开始任务。
2. 进行中 - 在 Word 文档中，任务被认领或被指派。
3. 待测试 - 任务被初步完成；例如在文档中，认领或被指派者评论"已完成，需要进一步测试"。
4. 已完成 - 任务彻底完成；在文档中，要求划掉对应已完成的任务，并且在对应任务评论处点击右上角打勾。

任务管理遵循以下规则：
* 每个人都可以添加新的任务。
* 每个人都有权讨论任务的存废。
* 每个人都有认领任务的权力。
* 每个人被指派后，都有因故拒绝任务的权力，但需要提供缘由
* 认领或被指派后，因故无法继续完成任务，需要提交详细的任务上下文，并且由自己或让管理员指派一位成员继续完成。
* 指派任务时，需要在聊天软件里提及。
* 成员被指派后，必须在三个小时内作出回应。
* 增加任务时，需要提供最基本的任务上下文。

### 开发流程概览
我们的开发工作以一周为一个迭代周期 (Sprint)，每个迭代包含以下例会：
1. （可选）迭代计划会 (Sprint Planning)
    - 时间: 每个迭代周期的第一天。
    - 占用时间: 5分钟至1小时不等。
    - 内容: 查看任务池，明确目标和任务分工。
    - 产出: 新的任务和更细化的需求。

1. （可选）每日站会 (Daily Standup)
    - 时间: 每天。
    - 占用时间: 几分钟。
    - 内容：围绕以下问题
        - 昨天我完成了什么工作？
        - 今天我打算做什么？
        - 我遇到了什么障碍？可能由此产生的风险是什么？
        - 以及其他补充内容

3. （可选）成果展示 (Sprint Review)
    - 时间: 每个迭代周期的最后一天。
    - 占用时间: 5分钟至1小时不等。
    - 内容：总结本周期的结果，展示完成的功能，发现需要改进的目标。

这些会议可以通过文本或电话的形式进行。

其中，每日站会有以下细节：
1. 每位成员轮流回答以下问题
    - 昨天我完成了什么工作？
    - 今天我打算做什么？
    - 我遇到了什么障碍？可能由此产生的风险是什么（如果有）？
2. 可选地，每位成员轮流思考以下问题，并给出陈述
    - 有没有针对某成员 (或团队) 的提醒？如果有，要提醒他 (或团队) 什么？
    - 还有没有别的要补充的？
3. 站会必须限制在 15 分钟以内。
4. 站会在**每个工作日的下午一点开始**。
5. 不需要等待主持人即可开始发言。
6. 站会的作用是**强制沟通，减少信息不对等**、**明确目标**（相当于弱化的**指差确认**）。
7. 每位成员必须在**15分钟内到场并发表讲话**，若有迟到，负责人会记录。
8. 可以提前发表，但是不要在**凌晨**发表。
9. 不要把会议想的过于严肃，叽叽喳喳是应该的。

#### 示例 1 
```
昨天完成的工作：把页面重新修整了一下。
今天打算：接入某接口。
遇到的问题：这傻逼接口文档烂爆了，可能要花点时间。

@lmt 服务器要续费了
@somebody 那个接口你做不了你叫别人做，你一直在拖延我的时间

我今天做的这部分工作不知道优先级高不高，如果不行我就换一个。
```
这时，如果你完成的工作优先级并不高，负责人会看到并直接指出，及时刹车。

#### 示例 2: 你因故无法工作
```
昨天：我跑了两趟医院，有些细节比较隐私不能透露。
今天：还要再跑一趟。

昨天估计的太乐观了，估计必须到后天可以回来工作。
```

### 要求与操作细则
* **新建任务** - 新建任务的最重要的目标是让接手者能在最短时间内继续开发，为此，确保你的记录具备以下特点:
    1. 清晰明了 - 避免过于冗长的说明，避免语病。
    2. 结构化 - 分成"任务简报"和"任务细节"，简报通常就是文档中的任务名称，而细节则是与任务关联的文档子页 (参见 Google Docs 操作指南)。

* **代码提交** - 参见开发周期.md。

* **成员因故暂时或永久无法开发** - 成员需要在任务记录与聊天群中记录以下内容:
    1. 当前任务状态
        * 描述任务进度，例如 "已经做到实现某接口的部分，相关的服务是..."。
        * 标明还要哪些部分未完成。
    2. 关键代码位置
        * 指明正在编辑的代码文件和核心代码片段的位置，例如 "在 Order 类的 xxx 函数"、"utils/order_utils.dart 的第 42 行"。
        * 如果涉及复杂逻辑，在代码关键位置添加注释，解释意图，或者指导他人如何续写。
    3. 未解决的问题 (如果有) 
        * 列举当前遇到的技术问题或设计决策点，例如 "注意，通过某方法调某函数，会报错，不知道为什么"、"一旦用 VSCode 打开这个文件，就无法高亮，用其他 ide 就没问题。"
        * 如果有相关的讨论或参考文档，附上链接或说明，例如 "我已经发现这个报错问题和库有关，这是库那边的issue链接"
    4. 后续开发建议
        * 提供接下来的开发建议，例如 "等某部分完成的时候，可能要先接接口才能继续做"。
        * 如果有未完成需求或相关功能，标明其优先级，例如 "可以先不做商户端的"。
    5. 参考文档与资源
        * 补充当前状态下，与任务相关的最新文档、设计图或者需求说明。
        * 如果任务依赖外部 API 工具，通过相关的使用说明或链接。

* **成员发现棘手问题** - 成员在发现棘手问题的时候，成员**必须**在群里报告问题。处理方式类似于上述的**成员暂时无法开发**。

* **实习生遇到问题** - 实习生遇到问题时，**严禁**通过私聊其中一位成员来解决问题，必须在群内沟通。**成员也不应该接受来自实习生私信的问题**。

### 责任与协作
* 开发者: 每位开发者有义务在无法继续任务时，主动记录上下文，确保任务能够顺利交接。
* 技术负责人: 负责检查任务上下文是否足够清晰，并确保接手者能够顺利继续开发。
* 接手者: 在接手时，先详细阅读上下文记录，**确保理解充分后再继续开发**；如果记录不清晰或不明确，**必须及时与其他人 (原开发、负责人) 沟通**。

### 示例：简单上下文记录模板
本示例适用于在聊天软件内快速汇报。
```
我这几天有急事，这个页面(附图)暂时做不了。

```

## 个人责任
个人责任不仅仅是对自己的工作认真负责，同时也是对他人、团队、项目的负责。团队认为人作为人，就是有自由决策的能力的。但是自由决策，不代表不需要为自己的决策和行为承担后果。**我们鼓励团队成员在职责范围内自主决策**。

### 遇到问题时的决策
对于成员在遇到问题时的决策，需要明确: 
- 无论是选择**隐瞒问题、自行解决问题，还是指出问题并与团队讨论**，每一个决定都会对项目、团队和你个人产生一定影响。
- 你需要承担自己决策的后果，包括可能造成的风险和问题。如果你选择隐瞒问题或擅自行动而导致更大的问题，你需要负责解决由此带来的后续影响。
- 在做出决策之前，请评估自己是否掌握了足够的信息。如果你不确定问题的全貌，请主动与相关责任人、上一位负责人或团队沟通，而不是盲目行动。
- **沟通可以避免因信息不对称导致的误解或错误。**

示例:

- 如果你发现代码中存在问题，但选择自己重构解决，请确保你已经理解了所有相关模块的逻辑和依赖关系。如果后续该模块出现问题，你需要承担由此带来的后果。
- 如果你发现问题但没有告知团队，后续问题影响到项目进度，你也需要为此负责。

### 备忘录

在针对问题做出决策前，请简单评估以下几点：  
1. **影响范围**：问题是否会影响其他模块或团队成员的工作？  
2. **问题紧急性**：问题是否需要立刻解决，还是可以等到会议讨论后再处理？  
3. **自身能力**：你是否有足够的技能和信息来解决问题？  

评估完毕后，你可以自由选择以下两种方法之一:

#### **a. 自行解决**  
如果问题在你的职责范围内，并且你有能力和足够的信息解决，你可以选择自行修复。但需要注意: 
- 确保你的解决方案不会影响其他模块或造成技术债务。 
- 在修复完成后，向团队汇报你的改动和解决思路。  

#### **b. 指出问题并沟通**  
如果问题超出了你的职责范围，或者你不确定自己是否能有效解决问题，请立即指出并与相关责任人沟通:   
- 提出问题的背景、可能的影响和你观察到的细节。
- 如果可以，提供解决建议，但不要擅自行动。  

### 认知边界
每位成员都需要清楚自己的能力范围和信息边界:
- 知道自己的职责范围：在职责范围内，你有权根据自己的判断处理问题，但超出范围的问题需要及时寻求帮助。
- 坦诚面对自己的能力限制：当你不确定是否有能力解决问题时，主动寻求团队支持，而不是冒险行动。
- 避免信息不足导致的错误：如果你对问题的背景或全局逻辑不够了解，擅自修复可能会引入新的隐患。因此，在做出决策之前，确保你已经掌握了足够的信息。

示例：

- 如果问题涉及到你不熟悉的技术或模块，请主动向相关领域的专家寻求支持，而不是盲目尝试。
- 如果你发现问题可能影响多个模块，请与团队讨论，而不是独自承担修复责任。

## 结语
感谢你花时间阅读这份工作指南。我们在各方权衡下制定了这些规则，它的目的并不是灌输规则，而是让团队化工作能够有条有理，不让成员们互相卡对方的脖子，最后实现效率提升。我们希望通过这些宽松的规则，使每个人都能找到自己的节奏与目标，同时也为目标贡献一份力量。

工作中发生问题，出现挑战是无法避免的。但是只要我们始终坚持沟通，保持理解，很多事情最后就能迎刃而解。如果你对本指南有任何疑问或建议，请随便提出，我们会根据实际情况进行调整和完善。
