# 直接 commit 的情况
- 只有核心成员被允许直接 commit。
- 只有紧急修复的情况允许直接 commit。

# APP端主分支 commit 须知 
如有上述直接commit的两种特殊情况，请按照下面两种需求进行填写内容：
- 需要进行更新打包时，直接提交需要按照 [Pull Request 内容格式规范](#pull-request内容格式规范) 的类型填写。
- 不需要进行更新打包时，直接提交不需要按照[Pull Request内容格式规范](#pull-request内容格式规范) 的类型填写。
#### 示例
```bash
# 添加功能并且发布正式版
git commit -m "feat: 添加用户登录功能（release）"

# 修复bug并发布内部测试
git commit -m "fix: 修复bug（alpha）"

# 不需要更新打包
git commit -m "添加用户登录功能"
```

# 自审核
- 对于部分被许可的成员，允许在合理的情况下自审核自己的 Pull Request。

# 从 `master` 分支创建一个新分支

将分支命名为 **分支类型/分支目标** 格式，例如：
`bugfix/page_not_found`
```bash
git checkout master
git pull origin master
git checkout -b bugfix/page_not_found
```

# 在新分支编写和提交代码
* 开发过程中请保持分支单一主题，避免多功能混杂。
* 编码结束后，git add、git commit 并推送到远程：
```bash
git add .
git commit -m "修复404页面找不到的问题"
git push origin bugfix/page_not_found
```

# 在 Github 上创建一个 Pull Request
* 在 PR 描述中指向具体的任务板位置。
* 由核心成员进行代码审核。如果有改进建议或问题，会在 PR 下方评论。
* 根据反馈修改代码后，重新推送到同一分支，PR 会自动更新。
* 审核通过后，核心成员会合并 PR。
* 每个 PR 只关联一个主题/任务，避免“巨型合并”。
* PR 标题和描述务必规范、准确，便于团队协作和追踪。

# 等待审核

- 审核通过后，在任务列表中把当前任务标记为 已完成。

# 分支用法
要添加新功能或者修复bug，现在要用分支。每一个分支维护一个主题，直到这个主题做完再合并

分支名称格式
[类型]/[具体需求]

```
例如
bugfix/fix_scroll_issue
feature/userpage
update/update to Java 21
```

功能合并后，删除本地和远程分支 (通常这时自动完成的)：
```bash
# 如果你的分支在本地
# 不要忘记推送标签和删除分支
git push --tags
git push origin --delete feature/historyfix
git branch -d feature/historyfix
```

参见 [Github 工作流](https://docs.github.com/zh/get-started/using-github/github-flow)
